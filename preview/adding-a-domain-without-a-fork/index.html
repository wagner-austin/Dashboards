Adding a domain without a fork

Austin Wagner

I built a risk-prediction service for loan covenants, then generalised it so a new subject is a registration rather than a fork. Two more domains have since been added without editing the shared training, explainability or streaming machinery at all.

Problem
A model service written for one subject usually has that subject's assumptions baked through it, so the second subject means a copy.
Result
Weather and esports added behind one protocol, reusing the original machinery unchanged. Covenant, the original, is still served directly.
Models
12 backends behind one interface: 7 classifiers and 5 regressors, swappable per request.
Data
40 real public datasets, not synthetic ones.
Stack
Python, PyTorch, XGBoost, LightGBM, Optuna, Kafka on Confluent Cloud.

The claim, stated exactly

Pluggability is easy to assert and the assertion is usually worth nothing, so here is the testable version: the second and third domains required no edits to the shared machinery. Weather and esports each implement one protocol and register. Covenant, being first, is served by the service directly and is not itself a plug-in.

That distinction matters because the interesting evidence is not "three things exist". It is that generalising an existing system did not require rewriting it, which only the two added afterwards can demonstrate.

Rules and models kept deliberately apart

Covenant compliance is exact rule evaluation: formulas, thresholds, frequencies. Breach risk is the learned path. They are separate code paths on purpose.

Conflating them would make a compliance answer probabilistic, which is worse than useless. A lender asking whether a borrower is in breach needs an exact answer from the contract terms, not a confidence score. The temptation is real because one model could nominally produce both.

Substitutable underneath, stable on top

The same idea runs through the model layer and the explanation layer. Twelve backends sit behind one interface, including gradient boosting I wrote from scratch competing against the production libraries in the same harness, and they are selectable per request.

Explainability follows the model rather than the endpoint: permutation importance for anything, tree explanations for tree models, gradient-based attribution for the neural ones. One contract, three strategies, chosen by what is actually loaded.

Training on 40 real public credit, loan, default and bankruptcy datasets rather than generated data is the unglamorous half. Synthetic data is the usual shortcut, and it flatters everything.

Record
